# AI Stack v0.8 — Autonomous Engineering Runtime

v0.8 turns cloud-worker leases into a fenced execution protocol and makes Server the durable authority for attempt ownership, cancellation, proof, and idempotent submission.

## Cloud task lifecycle

A task progresses through:

`queued → leased → preparing_workspace → running → verifying → uploading_result → completed`

Terminal failure/cancellation states remain durable. Worker-driven state transitions are validated and require an unexpired current lease fence.

## Lease fencing

Every claim generates a new UUID `lease_id` and increments `attempts`. Heartbeat, state updates, and completion require all of:

- task ID;
- worker ID;
- current `lease_id`;
- unexpired lease.

After expiry/reclaim, an old worker cannot heartbeat or publish completion. Cancellation clears the fence and becomes terminal immediately.

## Idempotency

`POST /platform/cloud/tasks` accepts `idempotency_key`. A partial unique index guarantees that concurrent retries with the same key resolve to the same durable task instead of creating duplicate engineering jobs.

Clients should generate a stable key for one logical submission and reuse it across transport retries.

## Portable Git workspaces

A cloud task may reference either an allowed existing Server workspace or an HTTPS Git repository plus optional safe ref/exact commit. The worker independently validates the repository URL/ref/commit, checks the host against `JARVIS_CLOUD_GIT_ALLOW_HOSTS`, creates a per-lease ephemeral checkout, and returns bounded tracked + untracked patch metadata.

Secrets are not accepted in repository URLs. Worker Git credentials remain worker-local.

## Model selection

Cloud payloads carry only a model/profile selector, never provider credentials. `auto` allows worker-local calibration. Named profiles resolve their own provider, endpoint, capability limits, and API-key environment on the worker.

## Execution proof

The Server stores the latest worker proof JSON on the cloud task. The worker proof includes lease acquisition, workspace identity, resolved route, local execution evidence, verification phase, and returned patch metadata. Proof is evidence of execution, not model chain-of-thought.

## Cron schedules

Server schedules use conventional five-field UTC cron semantics with lists/ranges/steps, Sunday `0/7`, and day-of-month/day-of-week OR semantics when both are restricted.

## Required validation

Production release requires executable coverage for:

- concurrent idempotent submission;
- wrong-worker/wrong-fence heartbeat rejection;
- expired-fence completion rejection;
- task reclaim with a new fence;
- terminal cancellation and non-reclaimability;
- valid state transitions and invalid-state 4xx responses;
- Postgres migration from the current schema;
- cross-repository CLI/Core/Server smoke tests;
- existing supply-chain and real Ollama/LiteLLM integration gates.
