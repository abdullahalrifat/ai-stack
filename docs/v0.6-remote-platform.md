# v0.6 remote agent platform

Server v0.6 extends the existing durable Runs engine with schedules, external cloud workers, OpenTelemetry, and empirical route calibration without creating a second coding-agent execution engine.

## Reviewed Runs remain the primary Server execution path

Use `/runs` when Server should execute a task. Existing sandbox creation, evidence gates, streamed events, cancellation, approval/discard, checkpointing and recovery remain authoritative.

Scheduled work is converted into an ordinary Run and submitted through the same worker path.

## Durable schedules

The authenticated platform API stores schedules in Postgres. A schedule contains a normal Run payload plus exactly one timing mode: a fixed interval or five-field cron expression. The platform monitor claims due schedules with `FOR UPDATE SKIP LOCKED`, advances `next_run`, creates a normal Run and calls the existing `submit_run` path.

This means scheduled writes retain the same review/sandbox behavior as interactive Runs.

## Cloud task leases

Cloud tasks are for external workers that run Jarvis on another machine. They are separate from reviewed Server Runs by design.

Lifecycle:

1. client submits a cloud task;
2. worker claims the oldest queued task or an expired running lease;
3. Server records worker id, expiry and attempt count;
4. worker heartbeats while executing;
5. worker reports structured completion or error;
6. expired leases can be reclaimed by another worker.

The Python SDK implements both client and worker sides of this protocol. A cloud worker may use its own local/remote model configuration while Server remains the durable coordination authority.

## OpenTelemetry

Server always retains a JSONL trace fallback. When `OTEL_EXPORTER_OTLP_ENDPOINT` is configured and OpenTelemetry packages are installed, traces are exported through OTLP as well.

v0.6 instruments:

- agent execution;
- tool execution;
- platform reconciliation;
- schedule submission;
- cloud claim/heartbeat/completion operations.

No secrets or unbounded model/tool payloads should be placed in span attributes.

## Automatic route calibration

The platform monitor converts terminal durable Runs into route observations exactly once per run id. It prefers the effective model recorded in the durable `route_selected` event rather than the requested model selector.

Measured signals include terminal success, answer-audit failure, latency, token/tool failure fields when available, and task category. Once a route has enough samples, these measurements adjust heterogeneous expert candidate quality/latency scores.

Model self-confidence is not used as calibration evidence.

## Operations

The platform monitor starts from the FastAPI lifespan whenever the durable Postgres store is configured. Existing run reconciliation and client/channel workers continue independently.

Useful failure scenarios to test before production promotion:

- two API replicas claim due schedules simultaneously;
- cloud worker dies after claim and another worker reclaims the expired lease;
- stale worker attempts to heartbeat/complete a task now owned by another worker;
- Postgres restarts during platform reconciliation;
- OTLP collector is unavailable while JSONL fallback remains writable;
- scheduled write Run reaches `awaiting_approval` rather than bypassing review.

## Release requirements

Before merging/releasing the coordinated v0.6 line:

1. run unit tests and Postgres integration tests;
2. run the real jarvis-inference integration job;
3. verify `/capabilities` advertises schedules/cloud execution/telemetry features;
4. execute a real external cloud worker against Server;
5. verify route observations are idempotent by run id;
6. verify OTLP export with a collector;
7. pin Server to the final immutable jarvis-core v0.6 release artifact.
